## What holds

- Every private table cascades from GuestSession → Profile (migration.sql:739–784); AnalysisRun also cascades from the session directly. LlmCall has no profile link. No bytea/file column anywhere; CvText holds text + hash + parser version only.
- Composite owner FKs are real: Plan/JobRequirement → JobTarget(id, profileId) and AnalysisRun → Profile(id, sessionId) (migration.sql:763, 775, 781). Counterexamples tried: a plan/requirement naming another profile's JD (rejected), an analysis run naming another session's profile (rejected), an analysis run naming a demo profile (impossible: AnalysisRun.sessionId NOT NULL cannot match a demo's NULL sessionId), a session-owned demo (rejected by Profile_owner_xor_demo_check). MATCH SIMPLE leaves NULL jobTargetId/profileId unchecked, which is correct for the discriminated cases.
- Extensions are created in migration SQL (migration.sql:2–3). Vector values are always bound parameters; only constant identifiers go through Prisma.raw (vector.ts:12–16, 44, 51, 61–66). Dimension, finite values and nonzero norm are checked before SQL (vector.ts:22–31), and the column itself rejects wrong dimensions.
- The guard fails closed when TEST_DATABASE_URL is unset, empty, unparsable, non-postgres, non-loopback or not `_test`. localhost, 127.0.0.1 and ::1 are normalized to one label, so the same-DB comparison catches alias pairs. The server-side current_database() check runs before TRUNCATE. Refusal messages carry no URL/credentials, and a failed migrate does not echo stderr.
- docker-compose credentials are documented local-only defaults bound to 127.0.0.1. The only `.env.local` readers are prisma.config.ts, scripts/db-size.ts and the test harness; all three load it into process env without printing anything.
- Ownership: every changed path is inside the backend paths or the U03 grant listed on board.md:20.

### Guard bypass attempts (round-2 focus 1)

None succeeded. Each attempt either fails to parse or is refused for a non-loopback label. All refusals are conservative.

- **Percent-encoded host** `127%2E0%2E0%2E1`: postgresql: is a non-special scheme, so WHATWG keeps the opaque host encoded and the label is not loopback. Refused, even though pg would decode it to loopback.
- **Percent-encoded database name:** pg uses decodeURI and the guard uses decodeURIComponent. These differ only on reserved characters, none of which is in `[a-z0-9_]`, and the server-side check requires the exact name (integration-db.ts:82).
- **Userinfo tricks** (`127.0.0.1:55433@evil/…`, `@evil#@127.0.0.1`): the guard and pg use the same WHATWG parser, so the real host is evil. Refused.
- **pg's pre-encoding step** (index.js:20–23): encodeURI preserves every delimiter, so the URL structure is unchanged.
- **pg's dummy-host retry** (index.js:30): it only triggers on strings the guard already failed to parse. Refused.
- **IPv6 forms:** `[::ffff:127.0.0.1]` serializes to `::ffff:7f00:1`, which is not loopback. Refused.
- **Trailing-dot host** `localhost.`: refused.
- **Unix sockets:** `%2F…` in the host gives a non-loopback label; `?host=/path` hits the allowlist; the `socket:` scheme fails the protocol check. All refused.
- **Empty host** (`postgresql:///x_test`, or `@/x_test` with credentials): the label is "" or the parse fails. Refused.

### Embedding-identity design (round-2 focus 2)

Pinning the single Gemini identity in the CHECK is **correct** for these reference columns. Architecture §12.3:345 requires local-hash-ngram-v1 to be a separate identity that is never mixed with Gemini vectors in a column, index or comparison. The CHECK therefore implements the rule rather than blocking D21. The fallback needs its own column(s) plus HNSW index in U08 (see R2-4).
